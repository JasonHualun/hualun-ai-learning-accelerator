# 苏格拉底追问误用实录 — 实操教学 vs 理论教学

## 事件日期
2026-08-01

## 背景
用户问 RAG / GraphRAG / LLM Wiki 的概念，我启动了 `hualun-ai-learning-accelerator` 以费曼教学法+苏格拉底追问模式讲解。

## 翻车经过
用户在学 **Obsidian**（工具操作类知识），我按 Skill 规定走了费曼四步：
1. 第一步「制造困惑」— 抛出反直觉事实（Obsidian 离线存储的理念）
2. 第二步「概念展开」— 双向链接、神经元类比
3. 第三步「类比+例子」— 超市货架 vs 大脑神经元
4. 第四步「苏格拉底追问」— ❌ 问了"跟传统模式比，哪一个更难坚持？"

**用户的反应：**
> "你是觉得我之前学过 chunk 是吗？然后苏格拉底追问是干嘛？这个问题我没看懂，跟知识点有什么关系？最难坚持是什么意思？"

## 根因分析

### 核心错误
我把 **"哲学式的态度追问"** 当成了苏格拉底追问，而不是 **"边界验证题"**。

| 正确的苏格拉底追问 | 我犯的错 |
|---|---|
| 考理解深度：什么情况下这个方法不成立？ | 考个人态度：你最难坚持的是什么？ |
| 考应用边界：这个工具有什么死穴？ | 考抽象反思：如果理念变了世界会怎样？ |
| 给出具体场景让用户判断 | 问毫无上下文的态度问题 |

### 为什么错
- **"最难坚持的是什么？"** 不是知识点的考核题，这是心理咨询式的问题
- **Obsidian 是工具课**，不需要学生去"反思态度"，需要知道工具的局限性和适用场景
- 苏格拉底追问的本质是 **压力测试** —— 逼学生想清楚"什么时候别用这个东西"，而不是逼他自我反省

## 正确写法

对于 **工具/操作类知识**（Obsidian、服务器部署、编程语法等），苏格拉底追问应该这样设计：

```markdown
✅ 示例1（Obsidian）：
"当你积累了几千个互相连接的笔记后，你觉得 Obsidian 的检索速度会比文件夹模式更慢还是更快？有没有哪种类型的资料（比如纯图片库、长视频素材），它是完全不擅长管理的？"

✅ 示例2（Git）：
"Git 分支模型适合团队协作，但如果你的项目只有你一个开发者，而且每天只改几行代码，你觉得 Git 的优势还能发挥出来吗？什么时候它会反而成为负担？"

✅ 示例3（RAG 架构）：
"RAG 可以解决大文档检索的问题。但如果你的知识库每天更新100条新内容，每次都要重新向量化，你觉得 RAG 在实时性上会有什么瓶颈？有没有比 RAG 更适合高频更新场景的方案？"
```

## 分流规则（已写入 Skill SKILL.md）

进入费曼第四步前，必须先判断知识点类型：

- **A类：抽象原理/概念类**（博弈论、控制论、GraphRAG 原理）→ 标准苏格拉底路径：逼出概念深层逻辑和理论失效场景
- **B类：工具操作/工作流类**（Obsidian 使用、API 调用、编程语法）→ 场景边界验证路径：展示工具的局限性，回答"什么时候别这么做"

**两种都禁止的行为：**
- ❌ 不问哲学式反转（"如果改变了X，Y会变成什么样"）
- ❌ 不问态度/反思问题（"你觉得最难的是什么"、"你有什么感悟"）

## 教训

**费曼教学法 + 苏格拉底追问 的组合适用于理论学习，但不适用于工具实操。** 
实操类的结尾考核应该是边界验证，而不是哲学追问。Skill 里的第四步已经据此增加了 A/B 分流，但这个反面教材应留存供未来 Agent 对照自查。
